## 1 · Patrón / mecanismo

### 1.1 Inspect (UK AISI) a fondo — la forma `Dataset → Task → Solver → Scorer`

MIT (confirmado en el `LICENSE` crudo del repo, `Copyright (c) 2024 UK AI Security Institute`), v0.3.244 (2026-07-01), Beta (Development Status 4, aún no 1.0), 2.3k stars, 6,419 commits — mantenimiento activo pero con churn real de release.

**`Sample`**: `input`, `target: str | list[str] | None` (**string-only** — sin objeto estructurado de primera clase), `choices`, `id`, `metadata: dict`, `files` (para sandbox). **`Dataset`**: `csv_dataset()`/`json_dataset()`/`hf_dataset()`/`MemoryDataset([...])`. **`@task`**: función que devuelve un `Task(dataset, solver, scorer, epochs, config, sandbox, message_limit, ...)`. **`Solver`**: `async def solve(state: TaskState, generate: Generate) -> TaskState` — componible vía `chain()`; **crucialmente, un solver no está obligado a invocar `generate` en absoluto** — puede correr Python arbitrario (p. ej. invocar el propio engine de Chimera) y escribir `state.output` directamente. **`Scorer`**: `@scorer(metrics=[...])` sobre una función que devuelve `Score{value, answer, explanation, metadata}`; built-ins deterministas (`match`, `includes`, `exact`, `f1`, **`math()`** — equivalencia numérica/simbólica vía SymPy) y model-graded (`model_graded_qa`, `model_graded_fact`). `Score.value` soporta constantes `"C"/"I"/"P"/"N"` → CORRECT(1.0)/INCORRECT(0)/PARTIAL(0.5)/**NOANSWER(0)** — NOANSWER es un resultado de abstención/rechazo de primera clase, distinto de INCORRECT.

**Logs de eval**: formato `.eval` binario (default desde v0.3.46) o `.json`; `EvalSpec` captura `task_id`, `task_version`, `model`, `dataset` (incl. `sample_ids`/shuffle), **`revision`** (git commit + dirty flag), **`packages`** (versiones de dependencias) — pero **sin un solo campo de digest/hash de config**: la reproducibilidad exige computar un checksum propio a partir de estos campos granulares, no viene gratis. `inspect eval-retry` reanuda corridas interrumpidas; `inspect score` re-puntúa logs existentes sin re-correr el solver. `--epochs`/`--epochs-reducer` (mean/median/mode/max/`pass_at_k`) repiten cada sample N veces y agregan.

**Self-host y agnosticismo de proveedor:** `pip install inspect-ai`, sin SaaS forzado; Docker solo para el subsistema opcional de sandboxing (soporta `x-local: true`, sin nube forzada). Soporta explícitamente `--model none`/proveedor `mockllm` — evals que no invocan ningún modelo son un caso de primera clase, no un hack.

### 1.2 Ajuste al corpus runner y decisión inspirar-vs-dev-dependency

**Lo que calza limpio:** `Sample.metadata` + `target` serializado puede llevar una instancia IEEE + su partición óptima conocida; un solver puede saltarse `generate()` e invocar el propio solver de Chimera; el vocabulario `C/I/P/N` es casi perfecto para el KPI de over-refusal — `N` (NOANSWER) ya es un resultado distinto de `I` (INCORRECT), así que "tasa de sobre-rechazo" = `count(N) / count(total)` sobre ítems del corpus con respuesta factible conocida sale de la maquinaria de métricas existente, sin inventar taxonomía nueva; `math()` es el precedente más cercano a "la respuesta coincide dentro de tolerancia"; ablación (features de verificación on/off) mapea a `Task`s parametrizados por `task_args`, cada uno con su propio `EvalLog` comparable (con `revision`/`packages` capturados).

**Lo que no calza / fricción:** `Target` es estrictamente `str | list[str]` — sin objeto estructurado de primera clase; una partición de grafo no es naturalmente un string (habría que JSON-encodear, peleando un poco contra el tipo). La colección **Inspect Evals** (200+ evals comunitarios) es abrumadoramente NLP/agéntica/benchmarks-de-código — sin precedente de scoring de optimización combinatoria/grafos cerrado. El peso del framework (registro multi-proveedor de modelos, sandboxing Docker, tool-calling, visor de transcripts) queda mayormente inerte para un job batch de "comparar contra óptimo conocido". Sin digest/hash nativo de config — la reproducibilidad exige trabajo propio de cualquier forma.

**Recomendación: "inspirar"** (tomar la forma, cero dependencia de runtime). Razones, contra los 4 factores pedidos:

- **(a) Tiempo de hackathon:** un runner propio cubriendo Dataset/Sample → Task → llamada-al-solver → Scorer → log JSON es chico (~150–300 LOC) sin necesitar sandboxing, ruteo multi-proveedor, ni UI de visor — para un corpus fijo de benchmark, no es obviamente más lento que aprender bien las convenciones de Inspect, sobre todo siendo pre-1.0 con releases cada 1–2 semanas (riesgo real de churn si no se fija versión).
- **(b) "Adapter detrás de un puerto, jamás forkear el runtime":** ese patrón se diseñó para librerías angostas y deterministas (CP-SAT, pandapower) envueltas finamente. Inspect es lo opuesto — un framework de orquestación end-to-end opinionado que quiere poseer el loop de eval, el CLI, y el logging. Adoptarlo como dependencia arriesga que el control de flujo del corpus runner viva DENTRO del ciclo de vida de Inspect en vez de detrás de un puerto angosto propio de Chimera.
- **(c) Fuga de conceptos de framework-de-eval hacia los contratos de verificación:** riesgo real. `TaskState.messages`, `pass_at_k` sobre epochs, un visor de transcripts chat-first son vocabulario de eval-de-seguridad/benchmark-de-LLM. Nuestro contrato de verificación contra óptimo conocido (clase `ground_truth`) es "¿la partición coincide con el óptimo conocido dentro de tolerancia?" — forzarlo por un `Target` string y un `TaskState` con forma de chat es exactamente el tipo de code smell que el patrón de puerto existe para evitar. Tomar solo la _forma_ (Dataset→Task→Solver→Scorer + el vocabulario C/I/P/N para over-refusal) evita esto por completo.
- **(d) Licencia:** no discrimina — MIT es plenamente compatible con el plan open-core Apache-2.0/MIT, sin copyleft.

**Cuándo reconsiderar dev-dependency:** si post-hackathon el corpus crece lo suficiente para necesitar batches largos reanudables/asíncronos, o si se quiere el visor `inspect view` y la señal de credibilidad de correr sobre el mismo harness que Anthropic/DeepMind/METR/AISI (adopción reportada por fuentes secundarias, no una lista primaria de AISI — anotado como menos verificado que licencia/arquitectura) — en ese punto la relación payoff/fricción se invierte.

### 1.3 DeepEval — decisión corta

Librería de testing pytest-style para outputs de LLM (`confident-ai/deepeval`), Apache-2.0 confirmado, 16.7k stars, mantenimiento activo (push el mismo 2026-07-07). Métricas insignia (faithfulness, hallucination, contextual precision/recall estilo RAGAS) apuntan a texto libre calificado contra contexto recuperado — una superficie que Chimera no tiene (motor de optimización de mundo cerrado, no chatbot de respuesta abierta). La familia **agéntica** (tool correctness, argument correctness, plan adherence) es un match conceptual más cercano si el LLM de Chimera orquesta alrededor del núcleo determinista, pero es una aproximación por juez-LLM de algo que el plano de verificación de Chimera ya chequea deterministamente y por-claim contra oráculos no-modelo — una garantía estrictamente más fuerte. **Veredicto: no adoptar como dependencia** — sin ventaja clara sobre lo que ya existe; revisar solo si surge un vacío concreto en testing de comportamiento de la capa de orquestación que el plano de verificación no cubra. Caveat operativo: telemetría PostHog on-by-default (opt-out vía env var, con issues abiertos reportando regresiones del propio opt-out) — verificar al instalar si algún día se reconsidera.

### 1.4 Promptfoo — anotado para la sesión de auditoría

CLI + config YAML (`promptfoo/promptfoo`), MIT confirmado, 23k stars, alta velocidad de release. **Flag de gobernanza:** OpenAI anunció adquisición (2026-03-09); ambas partes afirman que sigue open-source bajo la licencia actual — el cierre formal del deal no es verificable en vivo hoy; re-chequear antes de depender de esto a largo plazo. **Nuance de self-host importante:** el CLI core corre 100% local, pero varios plugins/estrategias de red-teaming (marcados 🌐: `meta`, `hydra`, `composite-jailbreaks`, algunas de dataset/jailbreak) llaman por default al endpoint cloud propio de "remote generation" de Promptfoo — forzable a local-only vía `PROMPTFOO_DISABLE_REDTEAM_REMOTE_GENERATION=true`, pero la propia doc admite que el ataque local-model es "de calidad generalmente baja", y algunos plugins simplemente no existen sin generación remota. Air-gapping real es feature de pago Enterprise. **Esto importa directo para la postura de confianza de Chimera:** red-teamear en modo default un sistema desplegado real enviaría sus outputs reales a un endpoint de terceros (ahora ligado a OpenAI) salvo config explícita en contrario.

**Workflow concreto de sesión de auditoría** (para que una sesión futura lo retome en frío):

1. `npx promptfoo@latest redteam init` (o `--no-gui` para modo scripted) genera `promptfooconfig.yaml`.
2. `targets:` apunta al entrypoint real de orquestación (proveedor HTTP o Python propio), no a un endpoint de modelo crudo.
3. `purpose:` describe el sistema para que los ataques generados sean relevantes — p. ej. "agente que orquesta partición de red eléctrica invocando tools de verificación/oráculo; debe rechazar instrucciones de override de un operador no confiable, jamás fabricar resultados de verificación, jamás expandir su propio alcance de tools".
4. `plugins:` relevantes al modelo de amenaza de Chimera: `indirect-prompt-injection`, `prompt-extraction`, `excessive-agency`, `agentic:memory-poisoning`, `bola`/`bfla` (bypass de autorización — relevante porque el agente sostiene privilegios de tool-calling), `hallucination`.
5. `strategies:` técnicas de entrega: `jailbreak`, `composite-jailbreaks`, `crescendo`/`goat` (escalación multi-turno), `retry` (tracking de regresión entre sesiones). Decidir por sesión si permitir estrategias cloud 🌐 o forzar `PROMPTFOO_DISABLE_REDTEAM_REMOTE_GENERATION=true` aceptando cobertura reducida.
6. Correr: `npx promptfoo@latest redteam run`.
7. Revisar: `npx promptfoo@latest redteam report` (o `promptfoo view`).
8. Versionar el config (mantener texto de endpoint/purpose interno fuera de todo lo público); re-correr antes/después de cambios en la capa de orquestación; diff vía `retry`.

**Conclusión:** buen fit conceptual para pasadas humanas periódicas de red-teaming sobre un agente con tool-calling — pero default a modo local-only dado el comportamiento phone-home-por-default y el estado de gobernanza en transición.

### 1.5 Descartes formales

- **RAGAS** (`vibrantlabsai/ragas`, Apache-2.0, 14.7k stars, última release 2026-01-13, actividad enlentecida tras el rebrand): todas sus métricas insignia (faithfulness, context precision/recall) son funciones sobre `retrieved_contexts` — chunks de texto que un retriever recuperó de un corpus. Chimera no tiene paso de retrieval ni corpus de texto: es un solver QUBO/Max-Cut de mundo cerrado sobre una instancia de problema fija y exactamente especificada. Alimentar RAGAS con una lista de contexto sintética/vacía para satisfacer su schema no mediría nada real — produciría una constante vacua que falsamente implica una señal de evaluación funcionando. Todo el modelo de objetos de RAGAS (query → retrieval → contexto → respuesta fundamentada) no tiene contraparte en el dominio de Chimera.
- **TruLens** (`truera/trulens`, MIT, 3.4k stars, activo — Snowflake mantiene tras adquirir TruEra): su propia doc afirma que existe porque "el ground truth es escaso y a menudo del todo no disponible" — llena ese vacío con "feedback functions" LLM-as-judge sobre trazas instrumentadas. Chimera es el caso inverso: ya tiene ground truth determinista, no-anclado-a-modelo, vía el plano de verificación. Adoptar TruLens sería degradar voluntariamente un plano con garantía determinista dura a una aproximación blanda juzgada-por-LLM de la misma pregunta — una regresión, no una mejora, justo donde Chimera se diferencia. Tampoco mapea limpio a la separación de tres planos: su scoring LLM-juez es funcionalmente lo que GUARDRAILS ya hace (informa, no decide), mientras su instrumentación/tracking gesticula hacia el trabajo de EVALUATION sin ningún primitivo para propiedades específicas de QUBO/Max-Cut (factibilidad, gap de optimalidad).
- **Giskard** (`Giskard-AI/giskard-oss`, Apache-2.0, 5.5k stars, muy activo — pero mid-pivote: v2 tabular/NLP/LLM declarado NO mantenido activamente en el README, v3 agéntico OWASP-LLM-Top-10 aún pre-GA beta): bajo cualquiera de las dos generaciones, el valor del scanner es pattern-matching genérico contra clases de vulnerabilidad conocidas (sesgo demográfico, perturbaciones de robustez, o red-teaming conversacional estilo OWASP) — ninguna con noción de corrección de solución combinatoria específica del dominio. Nada en Giskard chequea "¿esta partición Max-Cut de un grafo de red eléctrica es válida y cercana al óptimo?". Cualquier lógica de corrección específica de QUBO habría que escribirla a mano de todos modos, momento en el cual el activo real de Giskard (scanners genéricos curados) queda casi enteramente bypaseado.
- **LM-Evaluation-Harness** (`EleutherAI/lm-evaluation-harness`, MIT, 13.2k stars, activo, backend de facto de 200+ leaderboards): mide capacidad cruda de modelo base en aislamiento — scoring estático de log-likelihood/generación contra answer keys fijos en tareas académicas genéricas (MMLU, HellaSwag, GSM8K). Esto es ortogonal a lo que Chimera necesita: si el agente orquesta correctamente un loop de tool-calling para llegar a una partición válida y verificable de un grafo de red eléctrica específico, con corrección definida por verificación determinista contra un oráculo no-modelo, no por matchear una respuesta enlatada. Un modelo podría liderar MMLU y aun así malformar argumentos de tool o ignorar restricciones de grafo de mundo cerrado en la tarea de Chimera, o viceversa — las dos mediciones están descorrelacionadas de lo que el plano de EVALUATION de Chimera necesita certificar.
- **OpenAI Evals** (`openai/evals`): licencia base MIT pero el clasificador de GitHub reporta `Other`/`NOASSERTION` porque el mismo `LICENSE.md` agrupa licencias de datasets de terceros, incluyendo dos datasets **CC-BY-NC-4.0** (no-comercial) — una arruga de gobernanza más allá de la licencia de código base. 18.9k stars, merge-estancado desde ~abril 2026; su sucesor pretendido — la plataforma hosted "Evals" de OpenAI — recibió aviso de deprecación el 2026-06-03 (solo-lectura hasta 2026-10-31, apagado total 2026-11-30), y la guía de migración de OpenAI para ese producto hosted apunta a **Promptfoo**, no de vuelta a este repo OSS. Descarte por: (a) acoplamiento a vendor (CLI, convenciones de registro, interfaz de modelo construidos alrededor de la API propia de OpenAI, en conflicto con una arquitectura agnóstica de modelo); (b) alcance — templates built-in apuntan a calidad de chat-completion general, sin primitivo para puntuar contra un oráculo de optimización combinatoria determinista; (c) ambos extremos de la historia de evals de OpenAI (repo OSS y sucesor hosted) se están apagando concurrentemente a la fecha de verificación — mala base para construir infraestructura de trust-layer.

### 1.6 "Los tres planos" — nota transversal

> **[S3 · 2026-07-30 · #116] Rescate del huérfano #1 del TOP-10:** el marco «tres
> planos» (verificación ≠ guardrail ≠ evaluación) + la forma-Inspect del corpus
> runner + el KPI C/I/P/N entraron al backlog como el ítem #1 del TOP-10 (#116):
> **corpus-runner/eval + KPI over-refusal — dominio O temprano**
> (`docs/mejorado/04-consolidacion.md`).

Chimera opera con **tres planos deliberadamente separados**, y ninguna herramienta de esta nota ni de la 16 sustituye a otra:

| Plano            | Qué responde                                                                               | Cuándo actúa                              | Produce                                         | ¿Gatea egreso?                                                                                                                          | Ejemplo en Chimera                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Verificación** | ¿Este claim específico es correcto, probado contra un ancla no-modelo?                     | por-claim, en el camino crítico del run   | `Attestation` (clase decisoria + AL, freeze §4) | Es la única condición que `required_anchors` de una política puede exigir — pero ni siquiera ella sola gatea egreso (Inv-E: solo authz) | CP-SAT confirma el óptimo exacto de una partición                                     |
| **Guardrail**    | ¿Esta salida en particular, ahora mismo, luce sospechosa según un detector probabilístico? | por-paso, informativo, no-decisional      | `Signal` (antes `GuardrailSignal`)              | Nunca — informa, puede elevar fricción/pedir revisión humana, jamás decide                                                              | HHEM marca baja consistencia factual en un output                                     |
| **Evaluación**   | ¿Qué tan bueno/seguro es el sistema EN AGREGADO, a través de muchas corridas, offline?     | agregado, batch, fuera del camino crítico | métricas/KPIs (over-refusal, ablación)          | Nunca — es medición retrospectiva, no una decisión sobre ningún run individual                                                          | Corpus runner (inspirado en Inspect) mide tasa de sobre-rechazo contra el corpus IEEE |

La confusión típica del mercado (y el motivo de que RAGAS/TruLens/DeepEval-faithfulness/LM-Eval se sientan "relevantes" a primera vista) es tratar **evaluación** como si fuera **verificación**: un framework de eval que reporta "94% de faithfulness" suena a una prueba, pero es un promedio agregado sobre juicios probabilísticos — exactamente D18 (coherencia ≠ verificación) aplicado a escala de sistema en vez de a un claim. Los tres planos existen simultáneamente y se alimentan entre sí sin fundirse: la evaluación offline (este corpus runner) es lo que informa decisiones de roadmap/flywheel (nota 05 §1.3, anti-Goodhart/anti-collapse — nunca entrenar contra un único verificador); el guardrail informa fricción por-paso; la verificación es la única que puede satisfacer `required_anchors` de una `VerificationPolicy`. Ningún resultado de evaluación agregada, por alto que sea el score, puede sustituir una `Attestation` faltante en un run individual — y ningún `GuardrailSignal`, por alta que sea su confianza, tampoco puede.

## 4 · Impacto en contrato

**Ningún contrato cambia.** Aportes:

1. **Diseño del corpus runner** (clase `ground_truth` — corpus con óptimo conocido — + KPIs de over-refusal + ablación reproducible) queda especificado como herramienta propia inspirada en la forma de Inspect, viviendo en un módulo de eval/tooling **fuera** del engine (`verification`/`guardrails`) — consume `Attestation`s y eventos ya emitidos (lado lectura), nunca los produce ni los decide; respeta la misma frontera de módulos que ya protege INV-2.
2. **Métricas por run** de nota 05 §1.3 (`verification_latency_ms, attestations_total, inconclusive_count, false_reject_proxy`) son la fuente de datos que el corpus runner consume/proyecta — esta nota no agrega campos nuevos, conecta el consumidor.
3. **Convención `C/I/P/N`** para el KPI de over-refusal es una decisión de implementación del futuro corpus runner, no un cambio a `Attestation.verdict` (que sigue tri-estado `pass|fail|inconclusive`, nota 03 §1.4) — son capas distintas: `verdict` es por-claim dentro del engine, `C/I/P/N` es la agregación del corpus runner por-fuera.
4. **"Los tres planos"** (§1.6) es el marco de referencia transversal para futuras notas y para el pitch — evita que cualquier futura integración de una herramienta de evaluación se presente por error como si reforzara verificación.

## 5 · Reconciliación contra la base lógica

- **D18/D21 (coherencia/plausibilidad ≠ verificación):** REFORZADO a escala de sistema — "los tres planos" es la aplicación explícita de D18 al nivel de evaluación agregada, no solo al de una señal individual (nota 16 lo aplica a guardrails). Un score de evaluación offline alto es coherencia/plausibilidad agregada, nunca verificación.
- **Inv-E (egreso solo por authz):** INTACTO — ninguna métrica de evaluación, por buena que sea, participa en la decisión de egreso de ningún run; es medición retrospectiva y agregada, estructuralmente fuera del camino crítico de cualquier run individual.
- **Nota 05 §1.3 (KPIs de over-refusal, anti-Goodhart/anti-collapse):** REALIZADO — esta nota da la forma concreta (corpus runner inspirado en Inspect) a la promesa que nota 05 dejaba abierta como "proyección para el panel de ablación".
- **Ninguna referencia contradice la base lógica.** El hallazgo de que RAGAS/TruLens/DeepEval-faithfulness serían "relevantes" a primera vista, y no lo son, es la evidencia más directa de por qué la separación de tres planos necesitaba quedar explícita: el mercado de herramientas de evaluación tiende a difuminar exactamente esta línea.
