## 1 · Patrón / mecanismo

### 1.1 NeMo Guardrails — la taxonomía de 5 rails y su vocabulario real

Repo renombrado en vivo de `NVIDIA/NeMo-Guardrails` a **`NVIDIA-NeMo/Guardrails`** (redirect de GitHub silencioso — citar el nuevo org de acá en adelante). Apache-2.0 confirmado (`LICENSE-Apache-2.0.txt`), v0.23.0 (2026-07-01), 6.6k stars, 417 dependientes, mantenimiento activo.

La taxonomía oficial (`about-nemo-guardrails-library/rail-types`) confirma **exactamente 5** tipos:

| Rail          | Dispara sobre                            | Qué hace                                                   | Ejemplos reales de nombres de flow (config.yml)                                                                                  |
| ------------- | ---------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **Input**     | mensaje crudo del usuario, antes del LLM | rechaza o altera el input                                  | `self check input`, `jailbreak detection heuristics`, `mask sensitive data on input`, `llama guard check input`                  |
| **Dialog**    | flujo multi-turno (forma canónica)       | decide correr una acción / invocar el LLM / respuesta fija | flujos Colang de control de tópico (topical rails)                                                                               |
| **Retrieval** | chunks recuperados en RAG                | filtra/enmascara contexto antes del prompt                 | `mask sensitive data` aplicado a retrieval; filtrado de documentos                                                               |
| **Execution** | llamadas a tool/función                  | valida argumentos/resultados de la tool                    | validación de input/output de acciones (guardrails agénticos)                                                                    |
| **Output**    | respuesta ya generada                    | filtra, edita, o bloquea y reemplaza por rechazo           | `self check output`, `self check facts`, `self check hallucination`, `mask sensitive data on output`, `llama guard check output` |

Mecanismos detrás de esos nombres, con vocabulario verbatim de la config real: **hallucination rail** = SelfCheckGPT-style (N muestras extra + el propio LLM como NLI: original como hipótesis, muestras como evidencia); **fact-checking rail** = self-check LLM o backend **AlignScore** contra la base de conocimiento; **content safety rail** = clasificador LLM (Llama Guard / NemoGuard); **jailbreak protection** = capas (self-check LLM + heurísticas + modelo NemoGuard + terceros); **PII/sensitive-data** = integración **Microsoft Presidio**, con un `score_threshold` (default **0.6**) por tipo de entidad — el parámetro de confianza de primera clase más claro que existe en todo el diseño de NeMo.

**El hallazgo estructural que más importa para nuestro diseño:** NeMo **no tiene** un tipo uniforme "flagged + confidence" a través de todos los rails. Lo que existe es `log.activated_rails` — una opción de generación que expone qué rails dispararon, pensada para observabilidad/debug, no un contrato tipado de primera clase. Salvo el `score_threshold` de Presidio, **cada rail decide y ejecuta el bloqueo/reescritura por sí mismo** — autoridad de decisión unilateral dentro del propio mecanismo de detección. Es exactamente la fusión detección+decisión que nuestro tipo disjunto `GuardrailSignal`/`Attestation` existe para impedir.

### 1.2 Guardrails AI — validadores componibles y el registro como Hub

`Guard().use(ValidatorA, ValidatorB)` compone validadores sobre input/output. Cada `Validator` implementa `validate(value, metadata) -> ValidationResult`, con subtipos `PassResult`/`FailResult`. **Hallazgo relevante:** `FailResult` no tiene campo numérico de primera clase — solo `error_message`, `fix_value`, `error_spans`, `metadata: dict` genérico. Un validador que sí calcula un score (p. ej. `detect_jailbreak`, 0.0–1.0 contra `threshold` default 0.9) lo mete en el `metadata` dict, no en un campo tipado — hay un issue abierto desde hace ~2 años pidiendo exactamente esto (`guardrails-ai/guardrails#575`, aún abierto 2026-07-07).

**Vocabulario `on_fail` confirmado (8 valores):** `REASK` (re-pedir al LLM), `FIX` (usar `fix_value`), `FILTER` (descartar el campo), `REFRAIN` (devolver `None`), `NOOP` (loguear solo), `EXCEPTION` (levantar excepción), `FIX_REASK` (fix determinístico + re-validar), `CUSTOM` (callable propio). Igual que en NeMo: la decisión de qué hacer con el fallo vive **dentro** del propio validador, no separada como una señal que otro componente decide interpretar.

**El patrón realmente transplantable — el registro:** el decorador `@register_validator(name: str, data_type, has_guardrails_endpoint=False)` auto-registra un validador en un dict `validators_registry[name]` al importar — casi idéntico a nuestro patrón adapter-detrás-de-puerto. El **Guardrails Hub** (`guardrailsai.com/hub`, ~70 validadores namespaced por org) es la capa de distribución sobre ese registro: cada entrada declara nombre, tipo de contenido compatible, **tag de infraestructura** (rule-based / local-ML / remote-LLM), y **tags de categoría de riesgo** (Etiquette, Brand Risk, Factuality, Formatting, Invalid Code, Jailbreaking, Code Exploits, Data Leakage). Instalación vía `guardrails hub install hub://<namespace>/<validator>`.

**Nuance de self-hosting:** el runtime `Guard`/`Validator` y validadores propios son 100% self-hosteables (incluso un modo servidor Flask standalone desde v0.5.0). Pero instalar cualquier validador del Hub exige generar una API key gratuita en `hub.guardrailsai.com/keys`, persistida en `~/.guardrailsrc` — no es un paywall, pero sí una **puerta de registro externo obligatoria** específicamente para la función de distribución/registro.

### 1.3 Síntesis — vocabulario de `GuardrailSignal.name` y forma del registro

Ninguna de las dos librerías se integra como dependencia (§2). Lo que se porta es forma:

**Vocabulario de `name` — convención `{etapa}.{mecanismo}`:** primer segmento tomado de la taxonomía de 5 etapas de NeMo (`input` / `dialog` / `retrieval` / `execution` / `output` — ya bien probada, mapea 1:1 a dónde en el pipeline dispara el guardrail); segundo segmento en snake_case tomado de la convención de nombres del Guardrails Hub (`detect_jailbreak`, `detect_pii`, `toxic_language`). Ejemplos concretos: `input.detect_jailbreak`, `output.self_check_hallucination`, `output.detect_pii`, `dialog.topic_control`, `retrieval.detect_pii`, `execution.tool_arg_check`. Esto le da al campo `name` (ya congelado como `str` libre en nota 04) precedente real en ambas mitades sin copiar la taxonomía completa de ninguna.

**Forma de un futuro registro de guardrail-adapters** (Fase 2, sin comprometerse este mes): tomar del Guardrails AI el patrón decorador-de-auto-registro por nombre + metadata por entrada (tag de **infraestructura** rule-based/local-ML/remote-LLM del Hub — operacionalmente importante para saber cuáles son genuinamente self-hosteables — y tag de **tipo de contenido**); tomar de NeMo la **etapa** declarada (una de las 5, no el concepto de Guardrails AI que no tiene noción de etapa, solo wrapping de input/output).

**La divergencia crítica — lo que NO se copia:** ambos frameworks funden detección con autoridad de decisión dentro del propio primitivo (NeMo: un rail bloquea/reescribe unilateralmente; Guardrails AI: `on_fail` deja que un validador suprima/altere el output vía `REFRAIN`/`FILTER`/`EXCEPTION`). Es exactamente la fusión que el tipo disjunto `GuardrailSignal`/`Attestation` existe para impedir (D18/D21/Inv-E). Un futuro registro de Chimera declara adapters que **solo producen** `{name, flagged, confidence, rung, detail}` — nunca un campo `on_fail`-equivalente que le dé al adapter autoridad de gatear egreso. Esa autoridad, si existe, vive río abajo en `VerificationPolicy`/authz — nunca dentro del adapter de detección. Es un rechazo informado de una decisión de diseño de ambos frameworks fuente, no un descuido.

### 1.5 El 1-pager white-box: por qué el self-host habilita una señal que ninguna API cerrada puede ofrecer

**El claim, acotado con precisión:** la detección de alucinación basada en entropía semántica — específicamente su variante barata, **Semantic Entropy Probes (SEPs)** — es una señal técnicamente creíble que es _estructuralmente imposible_ de correr contra una API de inferencia de terceros cerrada (acceso estilo OpenAI/Anthropic), y solo está disponible cuando se controla el stack de inferencia de un modelo de pesos abiertos. Es un foso real y defendible. También es, sin ambigüedad, **detección — nunca verificación**.

**Qué es la entropía semántica** (Farquhar et al., _Nature_ 630, 2024): muestrear K generaciones, agruparlas por **entailment bidireccional** (equivalencia de significado, no solapamiento léxico), y computar entropía sobre la distribución de _clusters_ — más principista que la consistencia naive multi-muestra (SelfCheckGPT) porque separa explícitamente "muchas formas de decir lo mismo" (entropía baja) de "muchas respuestas genuinamente distintas y arbitrarias" (firma de alucinación). Costo: 5–10x el cómputo de una generación única (K=5–10 generaciones completas por consulta) — usable hoy, a ese costo, contra cualquier modelo incluidas APIs cerradas (de hecho la librería open-source **UQLM** de CVS Health ya la embarca — esta parte de la técnica NO es nuestro foso).

**Qué agregan las SEPs — y por qué son white-box únicamente:** Kossen et al. (arXiv:2406.15927, 2024 — **paper de workshop de ICML 2024, no peer-review de track principal**, OATML/Oxford) muestran que se puede entrenar un probe lineal chico (regresión logística) sobre el **hidden state** del modelo — un vector de activación del residual stream de una capa tardía específica, capturado en una sola posición de token, de la ÚNICA generación que ya está ocurriendo — para predecir la entropía semántica sin muestrear K veces. Esto reduce el overhead de 5–10x a casi cero (un forward pass de probe medido en microsegundos/milisegundos, no generaciones completas adicionales).

**La trampa, que es nuestro foso:** esto exige **leer el residual stream del modelo generador real, en medio del forward pass**. Ninguna API de inferencia cerrada expone esto — no por un vacío incidental de producto, sino porque hacerlo filtraría mucho más sobre los internals de un modelo propietario que los logprobs que algunas APIs ya cuidan celosamente, y elevaría materialmente el riesgo de extracción de modelo para el proveedor. Al 07-2026, incluso el propio trabajo de punta de Anthropic para leer las representaciones internas de Claude ("J-space"/"Jacobian lens", Transformer Circuits, 2026-07-06 — literalmente un día antes de esta investigación) es explícito en que esa capacidad es solo-investigación-interna y no se expone a consumidores de API externos. Solo un despliegue self-hosted de pesos abiertos — donde controlamos el stack de inferencia — puede instalar los hooks necesarios para leer estas activaciones.

**El caveat que se aborda, no se esconde:** enfoques de "proxy analyzer" (p. ej. arXiv:2605.07209, 2026) pueden apuntar una lente white-box a un modelo lector self-hosted _separado_ que relee texto generado por cualquier modelo, incluidos cerrados, y obtener una señal real — pero esa señal apunta a fundamentación-en-fuente (groundedness), no a la incertidumbre propia del modelo generador sobre el significado de su respuesta. No recupera lo que el modelo generador realmente "sabía" internamente. Nuestro claim está acotado a ese objeto epistémico específico, y se sostiene.

**Divulgación honesta de madurez (decirlo en voz alta, no enterrarlo):** la entropía semántica completa sí tiene adopción productiva real (UQLM/CVS Health, Apache-2.0, publicada en JMLR/TMLR). Las SEPs en sí — la variante de un solo paso, overhead casi cero, basada en probe de hidden states — son un resultado académicamente creíble y reproducible (paper de workshop ICML 2024, código de investigación con licencia MIT en `github.com/OATML/semantic-entropy-probes`, pero **91% notebooks, ~4 commits totales, sin releases** — no hay paquete instalable, requeriría ingeniería propia para conectar con el stack de inferencia y entrenar probes por modelo/capa) — pero dos años después nadie lo ha productizado. Esa brecha ES la oportunidad: seríamos los primeros en productizar la única variante de esta técnica que un competidor de API cerrada no puede copiar.

**El encuadre no-negociable — SIEMPRE explícito:** un score de SEP es un `GuardrailSignal` (rung 5-6 en nuestra escalera): probabilístico, basado en modelo, informativo. Puede elevar fricción, disparar una revisión humana, o suprimir egreso-por-default — NUNCA puede acuñar una `Attestation`, porque una Attestation solo la produce verificación determinista anclada a un oráculo no-modelo (solver, traza de ejecución, dataset, motor de reglas). La entropía semántica dice que el modelo está _incierto_; nunca dice que el modelo tiene _razón_, y jamás debe poder lavarse a sí misma como un claim de certeza. Cada mención de esta técnica en el pitch debe llevar esta distinción explícita — confundir las dos socava la credibilidad de toda la arquitectura de confianza frente a jueces técnicos.

4. **Semilla explícita de un futuro registro de guardrail-adapters** (Fase 2, sin forma congelada): decorador de auto-registro por `name` + metadata de etapa/infraestructura/tipo-de-contenido, deliberadamente **sin** campo de autoridad de decisión tipo `on_fail` — anotado como idea de diseño, no comprometido.

## 5 · Reconciliación contra la base lógica

- **D18/D21 (coherencia/plausibilidad ≠ verificación):** REFORZADO — tanto NeMo como Guardrails AI, y los 5 detectores de la tabla, son ejemplos de mercado de exactamente lo que D18 describe: coincidencia entre modelos o score de un clasificador, nunca consulta a un ancla no-modelo. Ninguno de ellos podría, ni debería, producir una `Attestation`.
- **Inv-E / INV-3 (guardrail no gobierna egreso):** REFORZADO por contraste — el hallazgo de que NeMo y Guardrails AI SÍ funden detección con autoridad de decisión (bloqueo/reescritura unilateral dentro del propio rail/validador) es precisamente el diseño que Chimera rechaza a propósito; se documenta como una decisión informada de divergencia, no un descuido.
- **AnchorKind (sin `"model"`):** INTACTO — ningún detector de la tabla, ni SEPs, califica como ancla; los cinco y las SEPs quedan, por diseño, fuera del puerto `Verifier` y dentro de `GuardrailSignal` exclusivamente.
- **Ninguna referencia contradice la base lógica.** El hallazgo más importante de esta nota (NeMo/Guardrails AI funden detección+decisión) es un dato sobre esas herramientas — confirma por qué la separación de tipos de Chimera es la decisión de diseño correcta, no una sobre-ingeniería.
