## 1 · Patrón / mecanismo

### 1.1 OPA (Open Policy Agent) a fondo

CNCF **graduated**, Apache-2.0. Rego —el lenguaje de política— es **Datalog** extendido sobre documentos JSON: no Turing-completo por diseño (como SQL), lo que garantiza terminación predecible de la evaluación.

**Decision logs** (`management-decision-logs`): cada decisión emite un `EventV1` con `decision_id` (traza única), `trace_id`/`span_id` (W3C trace-context), `path` (ruta jerárquica de la regla evaluada), `input`/`result`, `timestamp`, `metrics`, y — el campo que más importa para Chimera — **`bundles[<name>].revision`**: la revisión exacta del bundle de política vigente en el momento de esa decisión, adjuntada automáticamente sin config extra. Sinks: consola (`decision_logs.console: true`), servicio HTTP remoto (POST periódico de arrays JSON gzip, tamaño/intervalo configurables), o plugin custom.

**Bundle API** (`management-bundles`): un bundle es un `.tar.gz` con `.rego` + `data.json` + `.manifest` (JSON) + opcional `.signatures.json`. El `.manifest` tiene schema publicado: `revision` (string, típicamente un hash de git), `roots` (prefijos de path que delimitan el alcance del bundle), `rego_version`, `metadata` (libre). Distribución: OPA hace polling `GET <service>/<resource>` con **ETag/If-None-Match** (304 si no cambió) o **long-polling HTTP** (10s default). **Firma de bundle**: `.signatures.json` es un array de JWTs (uno por bundle firmado); el payload del JWT lista cada archivo con su hash SHA-256 (`files: [{name, hash, algorithm}]`) + `scope`/`iat`/`iss`/`keyid`; la activación verifica (a) firma del JWT, (b) que la lista de archivos del JWT coincide EXACTO con los archivos presentes, (c) hash de cada archivo — todo o nada, atómico. Existen también **delta bundles** (`patch.json` con ops JSON-Patch-like) para actualizaciones de datos de alta frecuencia sin re-empaquetar toda la política.

**La comparación que importa para `distributions/`:** el bundle de OPA da (a) distribución con hash verificado por archivo, (b) firma criptográfica del manifiesto completo, (c) correlación automática revisión↔decisión, (d) protocolo de distribución con ETag/long-poll. Es la referencia de forma correcta para cualquier futuro empaquetado de `VerificationPolicy` versionada — el freeze ya decidió NO adoptar OPA como runtime (nota 05 §2), pero esta forma (manifest con `revision`+`roots`, firma por hash-de-archivo, `policy_id`+digest estampado en cada decisión — ya congelado en nota 05 §1.2) es exactamente lo que un `distributions/chimera/` propio debe imitar si alguna vez necesita firmar/versionar bundles reales.

### 1.2 Cedar a fondo — "verificar la política misma"

Apache-2.0, repos `cedar-policy/cedar` (implementación) y `cedar-policy/cedar-spec` (formal-methods).

**Schema**: JSON que declara, por namespace, **tipos de entidad** (con `shape`: un `Record` de atributos tipados, marcables `"required": false`) y **acciones** (con `appliesTo`: qué `principalTypes`/`resourceTypes` acepta + forma esperada de `context`). Es el modelo de datos contractual contra el que razonan tanto el validador como las herramientas de análisis.

**Validación estática** (antes de ejecutar CUALQUIER política): dado un schema, el validador actúa como **typechecker del lenguaje de política** — detecta en tiempo de autoría: tipos/acciones no reconocidos, acción aplicada a un principal/resource al que no corresponde (mismatch de scope), atributos no reconocidos, acceso inseguro a atributos opcionales sin guarda, mismatches de tipo en operadores, literales de entidad inválidos para tipos enumerados; más warnings (cláusulas siempre-falsas, scripts mixtos/caracteres de control bidireccionales — defensa anti-Trojan-Source). Modo `strict` por defecto: prohíbe pasar strings no-literales a constructores de extensión (p. ej. rechaza `ip(principal.IPAddr)` porque el literal no es estáticamente conocido) — deliberadamente conservador para que las garantías de solidez se sostengan.

**Linaje de métodos formales:** el motor de autorización y el validador están **modelados en Dafny**; Amazon usó razonamiento automatizado para PROBAR propiedades de seguridad del propio motor (no solo de políticas individuales) — la prueba central: **solidez del validador** (si acepta una política, evaluarla contra cualquier request conforme al schema no puede producir las clases de error que el validador chequea), reforzada con un segundo modelo en **Lean**.

**Cedar Analysis (la pieza que Chimera cita — "probar propiedades del SET de políticas"):** el **Symbolic Compiler** traduce políticas+schema a fórmulas SMT que capturan TODO request posible que el conjunto de políticas permitiría, resueltas con solvers (CVC5); el compilador tiene pruebas Lean de su propia solidez y completitud. Sobre eso, el **Cedar Analysis CLI** prueba, entre dos policy sets: **Equivalente** (permiten exactamente los mismos requests), **Más/menos permisivo** (superset/subset estricto), **Incomparable**; y dentro de un mismo set: reglas `permit` sombreadas/muertas, condiciones imposibles, `permit`s siempre anulados por un `forbid`. Esto es "verificar la política misma" en sentido literal — una prueba matemática sobre el conjunto de reglas, no solo una decisión puntual.

### 1.3 Descarte formal — Casbin

Apache-2.0. Es una **librería** de control de acceso (ACL/RBAC/ABAC/ReBAC vía metamodelo PERM: Policy/Effect/Request/Matchers), con ports en +12 lenguajes y adapters de storage — no un motor de decision-logging ni de distribución de políticas.

**Por qué pierde frente al `VerificationPolicy` propio (confirmado contra su propia doc):**

1. **Sin audit/decision-log estructurado**: solo expone una interfaz `Logger` (`EnableLog`, `LogEnforce`, `LogRole`, `LogPolicy`) — un hook de debug para implementar vos mismo; sin `decision_id`, sin correlación bundle/revisión, sin sink remoto — habría que re-derivar a mano lo que OPA da gratis.
2. **Sin bundle/versionado/distribución**: las políticas son filas/archivos cargados por un adapter; sin manifest, sin firma, sin revisión-por-decisión.
3. **Sin verificación formal de la política misma**: a diferencia de Cedar, no hay validador schema-driven ni análisis simbólico que pruebe propiedades (equivalencia, no-interferencia) antes de correr.
4. **Mismatch de modelo**: PERM está hecho para control de acceso clásico (¿puede este sujeto hacer esta acción sobre este objeto?). La necesidad real de Chimera es un **router de exigencia de verificación** ("qué anclas y con qué rigor para este tipo de claim") — forzar eso al molde sujeto-objeto-acción de Casbin sería codificar mal conceptos de dominio propio (`side_effects`, `claim_type`, `min_rung`) como pseudo-sujetos/objetos.

### 1.4 Descarte formal — Kyverno

Apache-2.0, CNCF **graduated** (2024). Es un **admission controller nativo de Kubernetes**: intercepta `AdmissionReview` del API server vía webhook; políticas como CRDs en YAML (`validate`/`mutate`/`generate`, cada vez más sobre CEL en vez de JMESPath). Componentes: Webhook, Engine, Webhook Controller, Cert Renewer, Background Controller, Report Controllers.

**Por qué es un mismatch, no solo "más débil"**: toda su propuesta de valor está atada estructuralmente al ciclo de vida de admisión de K8s — evalúa políticas CONTRA MANIFIESTOS DE RECURSOS K8s en tiempo de admisión, usando CRDs como mecanismo de distribución y el webhook del API server como punto de enforcement. `VerificationPolicy` evalúa **claims de agente/solver dentro de un engine de aplicación** — no hay objeto K8s, ni admission request, ni cluster en ese camino de decisión. Adoptarlo exigiría levantar un control-plane K8s completo (API server, TLS de webhook, CRDs, background scanners) solo para obtener un motor de reglas cuyas features nativas (mutación/generación de objetos K8s, escaneo de estado de cluster) no transfieren a una decisión que no es sobre K8s.

### 1.5 OWASP Top 10 for Agentic Applications 2026 — mapeo integral riesgo→mitigación→capa

**Fuente oficial vigente:** `genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/` — OWASP Gen AI Security Project, **Agentic Security Initiative (ASI)**, publicado 2025-12-09, +100 expertos contribuyentes, activamente citado como el estándar vigente en julio 2026. **Distinto** de (a) el "Agentic AI — Threats and Mitigations v1.0" (feb-2025, guía de threat-model más antigua y menos autoritativa, superseded) y (b) el OWASP Top 10 for LLM Applications (genérico, single-turn, no agéntico) — el Top 10 Agéntico 2026 absorbe y reformula ítems de ambos (p. ej. ASI01 fusiona LLM01 Prompt Injection + LLM06 Excessive Agency) para sistemas multi-paso, autónomos, multi-agente. Esta es la lista que se usa de acá en adelante.
